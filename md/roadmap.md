# Tomorrow OS — Roadmap

**Статус:** черновик архитектуры и плана. Ветка `development` (переписывание на C с нуля).
**Дата фиксации решений:** 2026-09-02.

Документ описывает: цель, зафиксированные архитектурные решения, модель
безопасности, модель компонентов с поддержкой разных языков, спецификацию
своего UEFI-загрузчика и подробный план по фазам.

Связанные документы (завести по мере надобности):
`md/threatmodel.md`, `md/capabilities.md`, `md/abi.md`, `md/boot-protocol.md`,
`md/component-model.md`.

## 1. Что это

**Безопасная ОС-платформа, заточенная под запуск других ОС.**
Type-1 гипервизор со статическим партиционированием железа + микроядро с
capability-моделью в стиле seL4. Вместо `root` — **master controller**:
единственный начальный процесс, который держит стартовые capability и по
своей политике раздаёт права всем остальным. Никакого ambient authority,
никакого суперпользователя.

### Цели

- Минимальный TCB (загрузчик + микроядро), который реально можно
  прочитать построчно и со временем — формально специфицировать.
- Гости (Linux и др.) запускаются немодифицированными, на near-native
  скорости, изолированные друг от друга и от хоста.
- Любой драйвер, сервис, VMM — деприв, в своём адресном пространстве,
  с ровно теми правами, что выданы capability. Компрометация компонента
  не даёт власти над системой.
- Всё DMA — под IOMMU. Устройство не может выйти за отведённую память.
- Компоненты (всё, что вне TCB) можно писать на разных языках.

### Не-цели

- Совместимость с legacy BIOS, 32-бит, не-x86_64 (пока).
- Эмуляция полного PC-чипсета. Устройства гостю — только virtio или
  проброс через IOMMU.
- POSIX/Linux-ABI на самом хосте. Linux-софт крутится внутри гостя.

## 2. Зафиксированные решения

| Тема | Решение | Почему |
|---|---|---|
| Загрузчик | **Свой UEFI-загрузчик**, без GRUB/Limine | Часть TCB; хотим полный контроль и возможность подписи/измерения. |
| Модель безопасности | **seL4-стиль**: untyped memory → retype в типизированные объекты, capability + CDT, IPC через endpoints | Строгий учёт ресурсов, нет ambient authority, путь к формальной верификации модели. |
| Kernel heap | **Нет.** Память под ядерные объекты — из user-предоставленного untyped | Как в seL4: память ядра подотчётна userspace, детерминизм, верифицируемость. |
| Тип гипервизора | **Type-1, статическое партиционирование** (Jailhouse/Muen-стиль) | Простая и аудируемая модель изоляции; гибкий VMM — позже поверх. |
| VMM | Деприв, в userspace (NOVA-стиль). Ядро делает только `VMLAUNCH/RESUME` и прокидывает VM-exit | VMM вне TCB; его дыра не компрометирует хост. |
| Устройства гостю | **virtio + passthrough через IOMMU**. Эмуляции чипсета нет | Минимум кода, максимум скорости, DMA под контролем. |
| Язык TCB | C (загрузчик + микроядро) | Мало кода, аудируемо, путь к верификации (как seL4). |
| Языки компонентов | **Любой**, который умеет SysV AMD64 syscall и следует ABI | Изоляция адресным пространством + capability делает выбор языка на компонент свободным. |
| Целевая платформа | x86_64, UEFI, Intel VT-x + VT-d сначала (AMD позже) | Лучшая документация для хобби-разработки. |

### Открытые под-решения (определить до соответствующей фазы)

1. **Классический seL4 или MCS?** MCS (scheduling contexts как
   capability, reply-объекты) лучше для гипервизора и реального времени.
   Склоняемся к **MCS**. Решить до Фазы 4.
2. **Формат ядра для загрузчика:** свой flat-бинарь (как сейчас) или ELF64.
   ELF64 даёт секции/W^X/символы для отладки. Решить до Фазы 1. Рекомендация — ELF64.
3. **IDL для IPC** (свой мини-IDL + генератор стабов) или ручные стабы.
   Решить до Фазы 5.
4. **ASID/PCID стратегия** для гостей и процессов. Решить до Фазы 3/6.

## 4. Модель безопасности (seL4-стиль)

Полная спецификация — `md/capabilities.md`. Здесь — суть.

### 4.1 Объекты ядра

Все создаются только через `Retype` из `Untyped`:

| Объект | Назначение |
|---|---|
| `Untyped` | нераспределённый кусок физпамяти; источник всех остальных объектов |
| `CNode` | таблица capability-слотов процесса |
| `TCB` | поток (регистры, привязка к VSpace/CSpace, приоритет) |
| `Endpoint` | синхронный IPC-канал |
| `Notification` | асинхронные сигналы (биты) |
| `VSpace` + page tables (`PML4`/`PDPT`/`PD`/`PT`) | адресное пространство |
| `Frame` | страница физпамяти (4K/2M/1G), маппится в VSpace |
| `IRQControl` → `IRQHandler` | получение аппаратного прерывания как `Notification` |
| `ASIDPool` | пул ASID/PCID |
| `VCPU` | состояние виртуального CPU (VMCS + guest state) для гипервизора |
| `SchedContext` (если MCS) | бюджет времени как capability |

**Нет kernel heap.** Ядро не выделяет память динамически. Хочешь новый
`TCB` — предъяви `Untyped` достаточного размера и вызови `Retype`. Память
объекта подотчётна тому, кто дал `Untyped`. Это даёт строгий учёт и
верифицируемость.

### 4.2 Capability и права

- `cap = { объект, тип, маска прав, badge }`. Хранится в слоте `CNode`.
- Индекс слота (CPtr) — то, что процесс передаёт в syscall.
- Операции: `Copy` (с урезанием прав), `Mint` (Copy + badge), `Move`,
  `Mutate`, `Delete`, `Revoke`.
- **CDT (capability derivation tree):** ядро помнит, из какой capability
  выведена какая. `Revoke(cap)` рекурсивно удаляет все производные —
  мгновенно отзывает делегированные права. Без этого «нет root»
  превращается в «права раздали и забыли».

### 4.3 IPC

- **Endpoint, синхронный rendezvous.** `Send`/`Recv`/`Call`/`Reply`.
- **Fast path:** короткое сообщение целиком в регистрах (L4-стиль,
  ~8–16 слов), без аллокаций, без полного сохранения контекста.
- **Slow path:** IPC-буфер на поток — для длинных сообщений и передачи
  capability между процессами.
- **Badge:** при приёме сервер видит badge отправителя — знает, кто звонит,
  без доверия к содержимому сообщения.
- **Reply** (MCS: reply-объект; классика: reply-cap) — одноразовое право
  ответить конкретному вызывающему.
- `Notification` можно привязать к `Endpoint` — «ждать сообщение ИЛИ сигнал».

### 4.4 Прерывания и память как capability

- Драйвер получает `IRQHandler`-cap → прерывание приходит как
  `Notification`; ack — через syscall. Ядро не знает, что за устройство.
- Процессу отдают `Frame`-cap; он сам делает `VSpace.map(frame, vaddr, rights)`.
  Ядро не раздаёт страницы «просто так» — только по предъявлению cap.

### 4.5 master controller

При старте ядро создаёт **ровно один** процесс и передаёт ему:
всю `Untyped`-память, `IRQControl`, доступ к IO-портам/MMIO, `ASIDControl`.
Дальше **вся политика — в нём, в userspace**:

- по декларативному конфигу раздаёт untyped/память/IRQ драйверам, сервисам,
  VMM'ам и гостям;
- запускает компоненты из initramfs, следит за ними, рестартует;
- ведёт append-only аудит-лог (выдачи/отзывы caps, faults, старт/стоп VM);
- отдаёт TPM-quote для attestation.

Это аналог PID 1 + policy-manager, но **без привилегий** — просто
держатель начальных capability. Ядро политики не содержит.

## 5. Модель компонентов и поддержка разных языков

Полная спецификация — `md/component-model.md`. Суть:

**TCB (загрузчик + микроядро) — только C.** «Другие языки» — про всё, что
выше: драйверы, сервисы, VMM, гостевые агенты.

### 5.1 Что делает язык пригодным для компонента

Компонент — это отдельный ELF64-бинарь в initramfs. Достаточно, чтобы
тулчейн языка умел:

1. freestanding / `no_std` (без хостовой libc);
2. вызов `syscall` по System V AMD64 (аргументы в `rdi, rsi, rdx, r10, r8, r9`,
   номер в `rax`);
3. слинковаться статически по нашему linker-скрипту (entry `_start`).

Под это подходят: C, Rust (`no_std`), Zig, Ada/SPARK (zero-runtime
профиль), ассемблер, C++ (без исключений/RTTI). Изоляция адресным
пространством + capability + IOMMU означает: небезопасный по памяти
компонент не может навредить другим — можно смешивать свободно.

### 5.2 `libtomorrow` — рантайм компонента (на язык)

Минимальный набор на каждый язык:

- `crt0` (`_start`: разобрать переданный стартовый контекст → вызвать `main`);
- syscall-стабы (тонкие обёртки над `syscall`);
- IPC-хелперы (`call`, `recv`, упаковка/распаковка сообщений, передача caps);
- аллокатор поверх `Frame`-cap (свой heap компонента).

Эталон — на C (`user/lib/c/`). Rust-crate (`user/lib/rust/`) — вторым.
Остальные языки — по мере надобности, community-friendly.

### 5.3 Язык-нейтральный IPC

- Формат сообщения документирован по байтам (`md/abi.md`): фиксированный
  заголовок + типизированные поля + список передаваемых CPtr.
- **Мини-IDL + генератор стабов** (решение по под-вопросу 3): описываешь
  интерфейс сервиса в `.idl`, генерятся стабы для C и Rust. Аналог
  CAmkES / FIDL / Cap'n Proto, но крошечный, под наши нужды.
- Пока IDL нет — ручные стабы по спецификации формата.

### 5.4 Сборка

- `build.sh` / `Makefile` поддерживает per-компонент тулчейн: у каждого
  компонента свой `component.mk` с `LANG=c|rust|zig|...` и правилами.
- Итог сборки компонента — статический ELF64; кладётся в `initramfs`.
- Версия ABI пишется в заголовок бинаря; ядро/`libtomorrow` проверяют
  совместимость.

## 6. Свой UEFI-загрузчик — спецификация

Полная спецификация протокола — `md/boot-protocol.md`. Загрузчик — часть
TCB: маленький, аудируемый, без внешних зависимостей, подписываемый
(Secure Boot) и измеряемый (TPM PCR).

### 6.1 Что делает (порядок)

1. Инициализация консоли, баннер.
2. `LoadedImage` → `SimpleFileSystem` → корень тома.
3. Открыть и прочитать `kernel` (ELF64 или flat — под-решение 2) в память,
   выделенную как **`EfiLoaderCode`** (иначе NX-политика прошивки уронит
   прыжок в ядро; см. историю багов ниже).
4. Открыть и прочитать `initramfs` в `EfiLoaderData`.
5. GOP: перебрать режимы, отсеять непригодные пиксельные форматы
   (только 8-8-8-8 RGB/BGR), выбрать по `REQUEST_*` → списку приоритетов →
   скорингу (16:9 > 16:10 > 4:3 > прочее, потом площадь). *(Реализовано.)*
6. `GetMemoryMap` → `ExitBootServices` (ретрай при смене `MapKey`).
7. `SetWatchdogTimer(0,0,0,NULL)`.
8. Собрать `boot_info` и прыгнуть в ядро (SysV AMD64, `boot_info*` в `rdi`).

### 6.2 `boot_info` (передаётся ядру)

```
struct boot_info {
    u64 magic;                 // 'TMRW' + версия
    u64 memmap_addr, memmap_size, memmap_desc_size;  // копия UEFI memmap
    u64 kernel_phys, kernel_size;
    u64 initramfs_phys, initramfs_size;
    u64 rsdp_phys;             // ACPI
    struct { u64 base; u32 w, h, pitch_px; u32 format; } framebuffer;
    u64 loader_measurements;   // хэши для TPM/attestation (позже)
};
```

### 6.3 Известные грабли (уже пойманы, зафиксировать в коде)

- Память ядра — **`EfiLoaderCode`**, не `EfiLoaderData` (NX-политика →
  `#PF` на `call` в ядро → тройная ошибка).
- Выделять с запасом под `.bss`/стек ядра (flat-бинарь не несёт NOBITS);
  хвост аллокации занулять. При ELF64 — уважать `p_memsz > p_filesz`.
- virtio-gpu **не даёт** линейного framebuffer (только `Blt`). Для прямой
  отрисовки — `-vga std` / `VGA` / `bochs-display` / `ramfb`.
- `0x00FF0000` подразумевает BGRX; на RGBX-прошивке это синий — передавать
  `format` в ядро и упаковывать цвет по нему.
- UART 0x3F8 без инициализации: на QEMU пишет, на железе часто нет.

## 7. Стратегия устройств: только virtio + IOMMU-passthrough

- **Никогда** не эмулировать полный PC-чипсет.
- Гостю: либо **virtio** (console, blk, net, ...), реализованный в user-VMM
  и подключённый к хостовым сервисам; либо **проброс реального PCI(e)-устройства**
  через VT-d (свой IOMMU-домен на гостя, remapping MSI/MSI-X).
- Хостовые драйверы (NVMe, сетевая) — тоже в userspace, тоже под
  IOMMU-доменом: багнутый DMA ловится faultом, а не портит память.
- IOMMU обязателен до любого гостя с DMA и до любого passthrough.

## 8. Подробный план по фазам

Принцип: каждая фаза компилируется и проверяется отдельно; у каждой —
критерий готовности. План на 2–4 года соло. Треки «Тесты/CI» и
«Документация» идут параллельно всему.

### Фаза 0 — Фундамент и дисциплина (1–2 недели)

- Структура репо: `boot/`, `kernel/`, `lib/`, `user/` (`user/lib/`,
  `user/master/`, `user/services/`, `user/drivers/`, `user/vmm/`),
  `md/`, `tools/`.
- Сборка: профили debug/release; `-ffreestanding -mno-red-zone
  -mcmodel=kernel -fno-stack-protector -Wall -Wextra -Wshadow -Wvla`.
- CI (GitHub Actions): сборка + QEMU headless + grep маркера в serial → exit code.
- Отладка: `qemu -s -S` + `gdb`; скрипт `debug.sh`.
- Свои `memcpy/memset/memmove/memcmp` в `lib/`.
- Freestanding `kprintf` по serial.
- Завести `md/threatmodel.md`, `md/abi.md`, `md/capabilities.md` (скелеты).

**Готово когда:** `make && make test` в CI зелёный, `gdb` цепляется, `kprintf` печатает.

### Фаза 1 — Bring-up ядра, одно ядро CPU (1–2 месяца)

- **1.1** Загрузчик: `ExitBootServices` + `boot_info` (см. §6). Watchdog off.
- **1.2** Serial-логгер 16550. Резерв: кольцевой лог в углу framebuffer.
- **1.3** GDT + TSS: ring 0/3 сегменты, `RSP0`, ≥1 IST.
- **1.4** IDT + все 32 исключения: дамп регистров, error code, CR2, RIP,
  стектрейс по RBP. `#DF` на IST.
- **1.5** PMM: разбор memory map, buddy/bitmap, `pmm_alloc/free`.
  *Порт из Rust `main`: `pmm.rs`.*
- **1.6** Пейджинг, honest higher-half: всё ядро через `0xFFFF_8000_...`;
  отдельный direct-map физпамяти (`0xFFFF_8080_...` → phys) 2M/1G
  страницами; по таблицам ходить через direct-map, **не** полагаться на
  `phys == virt`. *Порт из Rust: `vmm.rs` map(), убрать identity-зависимость.*
- **1.7** Ранняя загрузка: разобрать `initramfs` (cpio/tar), найти
  `kernel`-объекты не нужно — но найти образ master controller.
- **1.8** `panic()`: file:line, дамп, стоп CPU, `cli; hlt`.

> **Нет kernel heap.** Ранний boot использует только статические буферы и
> PMM (страницами). Динамические ядерные объекты появятся в Фазе 4 через
> `Retype`.

**Готово когда:** ядро в higher-half без identity-обращений к своим
структурам; намеренный NULL-deref из ядра даёт читаемый дамп с RIP.

### Фаза 2 — Время, прерывания, первый поток (1–2 месяца)

- **2.1** ACPI static tables: RSDP→XSDT→MADT (LAPIC, IOAPIC, ISO), HPET,
  FADT, MCFG. **Без AML.** *Порт из Rust: часть `pci.rs` для MCFG.*
- **2.2** LAPIC: xAPIC/x2APIC, EOI, spurious, таймер, калибровка по
  HPET / CPUID(0x15). *Порт: `lapic.rs`, `hpet.rs`.*
- **2.3** IOAPIC: маршрутизация IRQ, маскирование. *Порт: `ioapic.rs`.*
- **2.4** Kernel threads: `context_switch` на asm (callee-saved + RSP + RIP).
  *Порт: `switch.s`, `scheduler.rs`.*
- **2.5** Планировщик: кооперативный → вытесняющий по тику;
  `Ready/Running/Blocked`; idle с `hlt`.
- **2.6** Синхронизация: спинлок с `irq_save/restore`, wait queue.

**Готово когда:** 3 kernel-потока печатают по таймеру; Blocked не жрёт CPU,
будится из обработчика прерывания.

### Фаза 3 — User mode и минимальный syscall (1–2 месяца)

- **3.1** Ring 3: `iretq` в user; `#GP`/`#PF` из ring 3 → убить процесс,
  не ядро. *Порт: `tss.rs`, идеи `process.rs` без хака `pid*0x1000`.*
- **3.2** `syscall/sysret`: `LSTAR/STAR/SFMASK`; entry на asm (`swapgs` +
  per-CPU, свап на kstack). *Порт: `syscall_entry.s`, `syscall.rs`.*
- **3.3** Per-process VSpace: свой PML4, kernel-половина общая; CR3 в
  context switch; PCID если есть.
- **3.4** ELF64-загрузчик: `PT_LOAD`, W^X (код RX, данные RW+NX; `EFER.NXE`).
- **3.5** `copy_from_user` / `copy_to_user`: единственная точка доступа к
  user-указателям; проверка диапазона и маппинга; аккуратно с `#PF`.
- **3.6** Заглушечные syscalls: `debug_write`, `exit`, `yield` (позже
  заменятся capability-интерфейсом).

**Готово когда:** бинарь из initramfs печатает через syscall и выходит;
fuzz со случайными аргументами syscalls не роняет ядро.

### Фаза 4 — Capability-ядро (сердце) (3–6 месяцев)

Спроектировать `md/capabilities.md` полностью **до** кода. Изучить
seL4 manual и дизайн NOVA.

- **4.1** Объекты ядра (§4.1) + `Untyped` + `Retype`. Определиться:
  классика или **MCS** (под-решение 1).
- **4.2** `CNode` + слоты + CPtr-адресация (guard/radix как в seL4 или
  плоско — решить).
- **4.3** `Copy/Mint/Move/Mutate/Delete/Revoke` + **CDT**.
- **4.4** IPC: `Endpoint`, fast path (регистры), slow path (IPC-буфер),
  `Call/Reply`, badge. `Notification` + bind.
- **4.5** `IRQControl`/`IRQHandler` → прерывание как `Notification`.
- **4.6** `Frame`/page-table объекты, `VSpace.map/unmap`.
- **4.7** `SchedContext` (если MCS): бюджет как capability.
- **4.8** Bootstrap: ядро создаёт master controller, передаёт стартовые
  caps (вся untyped, `IRQControl`, IO, `ASIDControl`).

**Готово когда:** два процесса общаются только через `Endpoint` от master
controller; без cap — ни память, ни IRQ; `Revoke` мгновенно отрубает
сервис; кривой CPtr → ошибка, не паника.

### Фаза 5 — Userspace-сервисы и драйверы (2–4 месяца)

- **5.1** `libtomorrow` на C (`user/lib/c/`) + Rust-crate (`user/lib/rust/`):
  crt0, syscall-стабы, IPC-хелперы, аллокатор поверх `Frame`-cap (§5.2).
- **5.2** Мини-IDL + генератор стабов C/Rust (под-решение 3), либо ручные стабы.
- **5.3** Драйвер консоли (framebuffer + PSF-шрифт) — сервис.
  *Порт: `console.rs`, `font.rs`, `font.psf`.*
- **5.4** Драйвер клавиатуры: PS/2 (xHCI — опционально, позже).
- **5.5** Таймер-сервис: `sleep`, периодические таймеры для клиентов.
- **5.6** Шелл — обычный процесс, ввод/вывод через IPC. *Порт: `shell.rs`.*
- **5.7** Блочный драйвер (NVMe) в userspace; DMA-буферы через `Frame`-cap.
- **5.8** ФС-сервис: read-only → writable. *Порт: `ramfs.rs` как временный.*
- **5.9** Реестр сервисов в master controller (выдача cap по политике).

**Готово когда:** ядро = планировщик + IPC + MMU + capability + IRQ + VMX-примитивы;
консоль/клавиатура/диск/ФС/шелл — отдельные процессы; убийство драйвера
консоли не роняет систему, master controller его рестартует.

### Фаза 6 — SMP (1–2 месяца)

- **6.1** Запуск AP: INIT-SIPI-SIPI, trampoline 16→64. *Порт: идеи `boot.s`.*
- **6.2** Per-CPU через `GS`/`swapgs`.
- **6.3** Планировщик per-CPU run queue; миграция; work stealing позже.
- **6.4** TLB shootdown через IPI.
- **6.5** Ревизия всех локов под многоядерность.

**Готово когда:** N потоков параллельно на N ядрах; стресс «мапь/размапливай
общую страницу с разных CPU» без stale TLB.

### Фаза 7 — IOMMU / VT-d (1–2 месяца)

- **7.1** DMAR из ACPI: DRHD, охват, RMRR.
- **7.2** Root/context таблицы, second-level page tables.
- **7.3** Домены: по домену на драйвер, позже на гостя. По умолчанию —
  всё DMA запрещено.
- **7.4** Драйверы Фазы 5 → на IOMMU-домены.
- **7.5** Interrupt remapping.

**Готово когда:** драйвер с багнутым DMA ловит IOMMU-fault; master
controller логирует его.

### Фаза 8 — Гипервизор MVP (2–4 месяца)

- **8.1** VMX enable: CPUID-проверки, `CR4.VMXE`, `VMXON` на каждом CPU.
- **8.2** `VCPU`-объект: VMCS (host/guest state, exec controls),
  entry/exit controls. Минимум перехватов.
- **8.3** EPT: 4-уровневые, 2M/1G; кусок физпамяти как «RAM гостя».
- **8.4** Цикл VM-exit: `VMLAUNCH` → exit → разбор → `VMRESUME`. Обработать
  CPUID, `HLT`, `RDMSR/WRMSR` (белый список), EPT-violation, VMCALL.
- **8.5** Тривиальный гость: блоб `cpuid` + запись в свою память + `hlt`.
- **8.6** Консоль гостя: `VMCALL(putc)` или эмуляция 16550 в user-VMM.
- **8.7** `VCPU`-cap: создание/запуск/стоп VM — только по cap от master
  controller. **Вся эмуляция — в user-VMM (деприв).** Ядро: только
  `VMLAUNCH/RESUME` + проброс exit'ов через IPC.

**Готово когда:** гость-блоб делает `cpuid`+`hlt`, вывод на консоли, VMM —
обычный процесс, убийство VMM не роняет хост.

### Фаза 9 — Настоящий гость (Linux) (3–6 месяцев)

- **9.1** Виртуальный LAPIC + таймер гостя (TSC offset / preemption timer);
  позже APICv + posted interrupts.
- **9.2** Фреймворк эмуляции MMIO в user-VMM: мини-декодер инструкций,
  диспетчер по гостевому физадресу.
- **9.3** virtio-транспорт (MMIO/PCI) в user-VMM: virtqueue, дескрипторы,
  нотификации.
- **9.4** virtio-console → консоль-сервис.
- **9.5** Загрузка Linux по x86/64 boot protocol: `bzImage`, `boot_params`
  (`e820` из EPT-раскладки, cmdline, initrd), прыжок в 64-бит entry;
  `console=hvc0`.
- **9.6** virtio-blk → блочный сервис/ФС.
- **9.7** virtio-net → software-свитч в userspace; per-домен фильтрация.

**Готово когда:** немодифицированный Linux грузится, даёт shell на
virtio-console, читает/пишет virtio-blk. **Главная веха «крутит другую ОС».**

### Фаза 10 — Passthrough устройств (2–3 месяца)

- **10.1** PCI(e) reassignment: отобрать у хоста, отдать домену гостя.
- **10.2** IOMMU-домен гостя: гостевые физадреса ↔ реальные.
- **10.3** MSI/MSI-X remapping → гостю.
- **10.4** Posted interrupts (APICv): доставка без VM-exit.
- **10.5** Эмуляция/фильтрация PCI config space гостю (BAR, MSI).

**Готово когда:** гостю проброшено реальное устройство (NVMe/сетевая),
near-native скорость, IOMMU держит устройство в памяти гостя.

### Фаза 11 — Хардненинг и policy-движок (постоянно, пик 2–4 месяца)

- **11.1** Цепочка доверия: UEFI Secure Boot → подписанный loader →
  измерение ядра/initramfs/master в TPM PCR.
- **11.2** Attestation: master controller отдаёт TPM-quote.
- **11.3** Policy-движок: декларативный конфиг — какие VM, какие ресурсы,
  какие межVM-каналы, какой passthrough. Без «дай всё».
- **11.4** Митигации: `CR4.SMEP|SMAP|UMIP|FSGSBASE`, `EFER.NXE`, W^X,
  KASLR ядра, ASLR user, guard pages, stack canary в ядре, CET если есть.
- **11.5** Append-only аудит-лог в отдельном домене.
- **11.6** Минимизация TCB: посчитать строки в кольце 0, вынести всё возможное.
- **11.7** Фаззинг в CI: syscalls, IPC, virtio-дескрипторы от гостя,
  ELF/ФС-парсеры. Непрерывно.
- **11.8** (амбициозно) Формальная спецификация capability-модели (TLA+/Alloy):
  инварианты «нет утечки прав», «Revoke полный». Полная верификация кода
  в стиле seL4 соло нереальна; спецификация модели — посильно.

**Готово когда:** по каждому пункту модели угроз — митигация или
осознанный принятый риск; фаззеры крутятся в CI неделями без падений ядра.

### Фаза 12 — Платформа и UX (бессрочно)

- Менеджер доменов (Qubes-стиль): список VM, ресурсы, запуск/стоп.
- GUI-мультиплексор: гость → offscreen-буфер, композитор хоста; ввод в
  фокусную VM.
- Брокеры с политикой: буфер обмена и передача файлов между доменами —
  через явное подтверждение.
- Сеть: per-домен firewall-VM.
- Шаблоны VM, CoW-снапшоты (EPT / блочный сервис).

## 9. Критический путь

```
0 → 1 → 2 → 3 → 4 → 5 ┐
                 4 → 8 → 9 → 10 → 12
        2 → 6 ──────────┘   (SMP — до серьёзного гипервизора)
        1 → 7 ────────────┘ (IOMMU — до passthrough и гостей с DMA)
11 — параллельно с 4 и далее, НЕ на конец
```

- **Фаза 4 — точка невозврата.** После неё «нет root» зафиксирован.
  Максимум времени на дизайн до кода.
- **8 (VMX MVP)** можно начинать сразу после 4, параллельно с 5.
- **6 и 7** — технически после 2 и 1; практически удобнее после 5.

## 12. Референсы

- **seL4** — capability-микроядро, формально верифицировано; манера
  untyped/retype, IPC, CDT. Читать: seL4 Reference Manual, "seL4: Formal
  Verification of an OS Kernel", дизайн MCS.
- **NOVA microhypervisor** — деприв VMM в userspace, быстрый; ровно наша
  модель гипервизора. Читать: "NOVA: A Microhypervisor-Based Secure
  Virtualization Architecture".
- **Muen SK** (Ada/SPARK) — сепарационное ядро со статическим
  партиционированием, «крутит другие ОС».
- **Jailhouse** — минималистичный партиционирующий гипервизор (~10k строк).
- **Genode** — ОС-фреймворк на capability поверх NOVA; `core` вместо root.
- **Bareflank**, серия "Hypervisor From Scratch" (Sina Karvandi) — поднятие
  VT-x с нуля.
- Intel SDM Vol. 3 (VMX, VT-d), UEFI Spec, ACPI Spec.
