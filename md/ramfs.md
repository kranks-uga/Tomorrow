# Файловая система (`src/ramfs.rs`)

Документация к файловой подсистеме Tomorrow OS. Это **RAM-only** файловая
система: диска нет, всё живёт в куче ядра. Начальный набор файлов приходит из
GRUB как multiboot2-модуль (tar-архив `initrd.tar`), разбирается один раз при
старте и дальше существует в heap.

Устройство — по модели Unix: **файл (inode) живёт отдельно от имени**.
Каталог — это лишь таблица «имя → `Arc<Inode>`». Поэтому удалённый файл,
который кто-то держит открытым, продолжает существовать, пока не закрыт
последний fd.

> Цель подсистемы — дать работающие `создание / редактирование / удаление`
> файлов без диска. Так устроены и ramfs/tmpfs в Linux (`/tmp`, `/dev/shm`):
> файлы только в памяти, после перезагрузки пропадают.

Syscall'ы, права на файлы (grants) и errno описаны в
[syscalls.md](syscalls.md); здесь — сама ФС.

## 1. Слои

```
 syscall (open/read/write/close)     shell (ls/cat/write/touch/rm)
        │ fd → OpenFile                     │ имя
        ▼                                   ▼
 ┌──────────────────────────────────────────────────────┐
 │ Пространство имён:  ROOT: Mutex<Vec<DirEntry>>       │
 │   DirEntry { name: String, inode: Arc<Inode> }       │
 │   lookup / list / create / delete / write            │
 └──────────────────────────────────────────────────────┘
        │ Arc<Inode>
        ▼
 ┌──────────────────────────────────────────────────────┐
 │ Inode { data: Mutex<Vec<u8>> }                       │
 │   read_at / write_at                                 │
 └──────────────────────────────────────────────────────┘
        │
        ▼
     heap ядра (1 МБ)
```

| Слой | Что делает | Где |
|---|---|---|
| Пространство имён | имя → inode | `ROOT`, `lookup`/`create`/`delete` |
| Inode | хранит байты, читает/пишет по смещению | `Inode::read_at` / `write_at` |
| Хранилище | где физически лежат байты | `Vec<u8>` в heap |

Имя используется **только чтобы найти inode** (`open`, команды шелла).
Открытый файл (`OpenFile` в fd-таблице процесса) держит `Arc<Inode>` и
позицию `offset`; `read`/`write` по fd к каталогу не обращаются. Syscall'ы
не знают, что внутри inode лежит `Vec`, — они зовут `read_at`/`write_at`.
Если когда-нибудь появится ФС на диске, меняется нижний слой, а не syscall'ы.

## 2. Путь данных: от GRUB до `ROOT`

```
 GRUB ──грузит── initrd.tar ──как multiboot2-модуль──▶ физ. память
   │
   ▼
 main.rs: разбор тега модуля (type 3)
   ├─ pmm::reserve(mod_start, mod_end)   ← чтобы PMM не отдал эти страницы
   └─ MOD_START / MOD_END                ← глобалы для ramfs::init
   ▼
 main.rs: heap::HEAP.init(1 МБ)          ← куча должна быть готова ДО ramfs::init
   ▼
 ramfs::init(): парсит tar по MOD_START, копирует данные в heap
   ▼
 ROOT: Vec<DirEntry>                     ← дальше живём только здесь
```

| Шаг | Что делает | Почему важно |
|-----|-----------|--------------|
| tag type `3` | читает `mod_start`/`mod_end` | это физ. адреса tar-архива в памяти |
| `pmm::reserve(mod_start, mod_end)` | помечает страницы модуля занятыми | иначе PMM выдаст их под другое → tar затрётся до парсинга |
| `heap::HEAP.init(...)` | инициализирует кучу (1 МБ) | `Vec`/`Arc` в `ramfs::init` аллоцируют из неё |
| `ramfs::init()` | парсит tar → `ROOT` | **строго после** heap и reserve |

После `ramfs::init()` память модуля больше не читается: все байты
скопированы в heap, поэтому ФС полностью writable.

## 3. Формат tar (USTAR), который мы читаем

Архив — последовательность записей по 512 байт. У каждого файла: один блок
**заголовка** + данные, добитые нулями до кратности 512.

| Смещение | Размер | Поле | Как читаем |
|----------|--------|------|-----------|
| `0` | 100 | `name` (ASCII, NUL-terminated, если короче 100) | до первого `0` или 100 байт → `String` |
| `124` | 12 | `size` (**восьмеричное** ASCII) | `parse_octal(base, off+124, 12)` |
| `512` | — | начало данных файла | `base + off + 512` |

Переход к следующему заголовку:

```
off += 512 + ((size + 511) & !511);   // заголовок + данные, округлённые вверх до 512
```

Конец архива — **пустое имя** (`name[0] == 0`): tar завершается двумя
нулевыми блоками, достаточно первого нулевого байта.

> Почему размер восьмеричный? Так устроен исторический формат tar.
> `parse_octal` читает `'0'..'7'` и останавливается на первой не-цифре.

## 4. Структуры

```rust
pub struct Inode {
    pub data: Mutex<Vec<u8>>,     // содержимое файла
}

struct DirEntry {
    name: String,
    inode: Arc<Inode>,
}

static ROOT: Mutex<Vec<DirEntry>> = Mutex::new(Vec::new());

pub const MAX_PATH: usize = 100;          // предел имени (= поле name в tar)
pub const MAX_FILE_SIZE: usize = 64 * 1024;
```

- **`Arc<Inode>`** — счётчик ссылок. Ссылки держат: запись в `ROOT` (одна) и
  каждый открытый fd (`OpenFile.inode`). Память файла освобождается, когда
  счётчик падает до нуля.
- **Два уровня локов.** `ROOT` защищает список имён, `Inode.data` — байты
  конкретного файла. Чтение одного файла не блокирует каталог.
- **`MAX_PATH`** общий для ФС и syscall'ов: `sys_open` копирует имя в буфер
  `[u8; MAX_PATH]`.

## 5. API

### Inode

| Метод | Что делает | Возврат |
|---|---|---|
| `read_at(offset, dst)` | копирует в `dst` с позиции `offset` | число байт; меньше `dst.len()` у конца, `0` за концом |
| `write_at(offset, src)` | пишет с `offset`: перезаписывает, при выходе за конец растит файл (дыра — нули) | `Some(новый конец)` или `None`, если превышен `MAX_FILE_SIZE` (тогда ничего не пишется) |

`write_at` обрабатывает все случаи одной схемой `resize` + `copy_from_slice`:
запись внутри файла, через конец и за концом (с дырой из нулей, как в Unix).

### Пространство имён

| Функция | Что делает | Возврат |
|---------|-----------|---------|
| `init()` | парсит tar по `MOD_START`, наполняет `ROOT` | — |
| `lookup(name)` | ищет запись, **клонирует `Arc`** и отпускает `ROOT` | `Option<Arc<Inode>>` |
| `list(cb)` | вызывает `cb(имя, размер)` для каждого файла | — |
| `create(name)` | создаёт пустой файл; отказ, если имя занято | `true`, если создан |
| `delete(name)` | убирает запись из `ROOT` | `true`, если удалён |
| `write(name, data)` | **заменяет** содержимое целиком (для шелла) | `true`, если найден |

## 6. Семантика: удаление открытого файла

`delete` убирает **только имя**. Inode живёт, пока на него есть хоть один
`Arc`:

```
 open("hello.txt")        ROOT ──Arc──▶ Inode ◀──Arc── OpenFile (fd 3)     счётчик 2
 rm hello.txt             ROOT    ✗     Inode ◀──Arc── OpenFile (fd 3)     счётчик 1
                          (ls не видит файл, read(fd 3) читает данные)
 close(3) / exit          Inode освобождён                                 счётчик 0
```

Процесс, завершившийся без `close`, тоже освобождает файлы: `reap` ставит
слот процесса в `None` → `drop(Process)` → `drop(fds)` → `drop(Arc)`.

Почему `offset` лежит в `OpenFile`, а не в `Inode`: два процесса, открывшие
один файл, читают его независимо, каждый со своей позиции.

## 7. Локи и порядок захвата

Правило: **никогда не брать `Inode.data`, держа `ROOT`**.

- `lookup` клонирует `Arc` и отпускает `ROOT` до возврата — вызывающий лочит
  `data` уже без него.
- `list` сначала копирует пары (имя, `Arc`) и отпускает `ROOT`, потом
  лочит `data` каждого файла по очереди, чтобы узнать размер.
- `create`/`delete` держат только `ROOT`; `read_at`/`write_at` — только `data`.

Так два лока никогда не берутся вложенно, и дедлока из-за порядка нет.

**Почему спинлоки не дедлочат с прерываниями (сейчас).** Шелл работает в
прерывании клавиатуры (IRQ → `cmd_*` → ramfs), а syscall'ы — в контексте
процесса. Опасный сценарий: процесс держит лок, приходит IRQ, обработчик
крутится на том же локе вечно. Сейчас он невозможен: `SYSCALL_MASK` сбрасывает
IF на входе в syscall, и пока ядро обрабатывает syscall, прерывания не
приходят. Это работает только на одном CPU: при SMP понадобятся локи с
гашением IF (как в `heap.rs`) или другой подход.

## 8. Команды шелла (`src/shell.rs`)

Шелл — доверенный код ядра: grants он не проверяет.

| Команда | Вызывает | Делает |
|---------|---------|--------|
| `ls` | `ramfs::list` | печатает `имя размер` построчно |
| `cat <file>` | `ramfs::lookup` | печатает содержимое (под локом `data`) |
| `write <file> <text>` | `ramfs::write` | заменяет содержимое целиком |
| `touch <name>` | `ramfs::create` | создаёт пустой файл |
| `rm <name>` | `ramfs::delete` | удаляет имя |

```
> touch note.txt
file created
> write note.txt hello world
written to file
> cat note.txt
hello world
> ls
hello.txt 18
readme.txt 12
note.txt 11
> rm note.txt
file deleted
```

## 9. Ограничения

1. **Нет каталогов.** Список плоский; `/` внутри имени — просто символ.
2. **Нет метаданных.** uid/gid/mode/mtime из tar не читаются. Права — не
   атрибут файла, а список grants у процесса (см. [syscalls.md](syscalls.md)).
3. **Лимит размера — на файл, не на ФС.** `MAX_FILE_SIZE` = 64 КБ для
   `write_at`, но 16 файлов по 64 КБ исчерпают кучу (1 МБ). `ramfs::write`
   из шелла и `create` лимитов не проверяют.
4. **`create` не проверяет длину имени.** Из шелла можно создать файл с
   именем длиннее `MAX_PATH`, который потом нельзя открыть через `open`.
5. **Длинные имена tar** (USTAR prefix, GNU long name) не поддерживаются —
   имя обрезается до 100 байт. В `init` предел пока записан числом `100`,
   а не `MAX_PATH`.
6. **Нет `seek`, `O_APPEND`, `O_TRUNC`, `O_CREAT`.** Позиция только растёт
   от 0; создать файл может только шелл.
7. **Всё пропадает при перезагрузке** — это свойство RAM-only ФС, не баг.
